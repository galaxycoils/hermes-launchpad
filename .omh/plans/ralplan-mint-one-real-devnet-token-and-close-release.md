# Final Consensus Plan — Mint One Real Devnet Token

## Scope and invariants

**Goal:** Create one target `Hermes Proof Token` (`HPT`, `🚀`) operation on Solana devnet, index it only after exact cryptographic verification, prove all postconditions, and close the release with exact-SHA evidence.

**“Exactly one” means only this operation:**

1. One target mint keypair generated in memory.
2. One wallet-signing event.
3. One broadcast attempt.
4. One successful Hermes `create_token` instruction for that target mint.
5. D1’s overall on-chain-token count changes from baseline `0` to `1`, with one row for that mint.

It does **not** claim global uniqueness of the name or symbol.

**Transaction invariant:** The prepared and confirmed legacy transaction contains exactly one top-level Hermes `create_token`, zero buy/sell/migration instructions, zero top-level System transfers, and only permitted Compute Budget instructions in addition to `create_token`.

**Dependency graph:** `WU-0 → WU-1 → WU-2 → WU-3 → WU-4 → WU-5 → WU-6`

### RED

Tests must fail for the current implementation and prove:

1. One mint keypair is generated per operation, remains memory-only, and is never regenerated by retry/reconciliation.
2. Name, ticker, emoji, URI, creator, mint, program ID, and cluster are locked before preparation.
3. Unsigned legacy simulation occurs before either signature using:
   - serialized transaction with missing signatures allowed;
   - RPC `simulateTransaction`;
   - `sigVerify: false`;
   - the prepared blockhash, not automatic blockhash replacement.
4. Simulation failure, non-devnet genesis, fee-estimation failure, or inadequate wallet reserve prevents approval/signing.
5. Debit presentation includes:
   - network fee from `getFeeForMessage`;
   - rent-exemption estimates for `Curve::LEN = 360`, SPL Mint `82`, and SPL Token Account `165`;
   - conservative upper bound: current fee plus estimated rents, a 10% rent cushion, and a 20,000-lamport fee cushion;
   - required post-create wallet reserve of at least `0.01 SOL`.
6. Approval is requested only after successful simulation and fee/rent calculation.
7. Declining approval causes zero signatures and zero broadcasts.
8. After approval, mint partial-signing and wallet signing occur immediately, with no intervening RPC/network operation or mutable metadata.
9. Wallet signing occurs once; raw broadcast occurs at most once.
10. The signed transaction ID is captured before `sendRawTransaction`.
11. Send failure, confirmation timeout, RPC timeout, and blockhash expiry preserve a structured repair record and enter `reconcile_only`.
12. Reconciliation queries signature status through blockhash expiry but never signs, resends, or regenerates.
13. Existing buy/sell `sendTx` behavior and heap-frame behavior remain unchanged.

### GREEN

Implement a create-only lifecycle:

`prepared → simulated → awaiting_approval → signed → submitted → confirmed → indexing → indexed`

with terminal alternatives:

`reconcile_only | declined | failed`

The structured, non-secret repair record is copyable and stored in `sessionStorage` under a mint-derived key:

```text
version
state
mint
creator
signature
blockhash
lastValidBlockHeight
locked metadata: name, ticker, emoji, uri
exact index payload
broadcastAttempted
index outcome/status
```

Private mint material is never included, logged, persisted, or transmitted.

`CreateTokenModal` displays a final “Approve and open wallet” summary containing:

- `Hermes Proof Token` / `HPT` / `🚀`;
- creator/fee payer and mint;
- program `9K5eAWBkrUJbUiUC8aM6xeuXM2ACj9XNHfbC1X6Scjgz`;
- verified devnet;
- fee, rent estimate, conservative total bound, current balance, and retained reserve;
- exactly one create, no buy/sell, no migration, and no additional SOL transfer beyond fees/rent.

### Acceptance

## WU-2 — TDD Exact Worker Verification and Atomic Indexing

**Dependencies:** WU-1

### Exact files

- Modify: `workers/chain.js`
- Modify: `workers/worker.js`
- Extend: `tests/worker/token-index.test.ts`
- Extend: `tests/unit/api-index-token.test.ts`
- Extend: `tests/client/create-token-modal.test.tsx`

No schema mutation is planned because WU-0 must prove the live unique index already exists.

### RED

Worker tests must reject:

1. Any RPC whose genesis hash is not the exact devnet hash.
2. Failed, unconfirmed, missing, or versioned transactions. Only legacy transactions are accepted; loaded-address handling is therefore out of scope.
3. Wrong or undecodable `create_token` discriminator. Exact bytes:
   - `[84, 52, 204, 228, 24, 140, 234, 75]`.
4. Transactions containing:
   - zero or multiple Hermes create instructions;
   - any other Hermes instruction;
   - any top-level System transfer;
   - any non-permitted top-level instruction beyond Compute Budget.
5. Any mismatch in the canonical account layout:

| Index | Account | Required role |
|---|---|---|
| 0 | config PDA = PDA(`"config"`, Hermes program) | read-only, non-signer |
| 1 | curve PDA = PDA(`"curve"`, mint, Hermes program) | writable, non-signer |
| 2 | target mint | writable, signer |
| 3 | curve ATA = ATA(mint, curve PDA) | writable, non-signer |
| 4 | creator | writable, signer |
| 5 | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` | read-only, non-signer |
| 6 | `ATokenGPvbdGVxr1b2hvZbsiqW5xWH25efTNsLJA8knL` | read-only, non-signer |
| 7 | `11111111111111111111111111111111` | read-only, non-signer |
| 8 | `SysvarRent111111111111111111111111111111111` | read-only, non-signer |

6. A curve account that has the wrong PDA, owner, discriminator, creator, mint, bump, reserves, completion state, or metadata.
7. Curve metadata that does not directly decode to request values:
   - name `Hermes Proof Token`;
   - symbol `HPT`;
   - URI `""`.
8. Null/partial/undecodable curve state; no row may be inserted and no `provenance: "onchain"` returned.
9. Sequential or concurrent duplicate requests producing different rows/responses.
10. Unrelated mints with the same ticker/signature prefix colliding on token ID.
11. Index failure being presented by the client as “live.”

### GREEN

1. Validate genesis hash before transaction/account verification.
2. Decode the exact legacy message, signer/writable roles, discriminator, and Anchor strings directly.
3. Require the curve account:
   - owner = Hermes program;
   - discriminator = SHA-256(`account:Curve`)[0..8], bytes `[191,180,249,66,180,71,51,182]`;
   - expected creator, mint, full metadata, reserves, completion state, and PDA.
4. Derive the D1 token ID collision-resistently as `mint-<full SHA-256 hex of mint>`.
5. Perform concurrency-safe idempotency:
   - `INSERT OR IGNORE` against unique `onchain_mint` and primary ID;
   - canonical readback by `onchain_mint`;
   - fail closed if readback is absent or differs;
   - return the same complete canonical payload for original, sequential duplicate, and concurrent duplicate calls, including `id`, `onchainMint`, `provenance`, `realSol`, and `complete`.
6. Remove the existing select-then-insert race and all request-trusted/null-decoder provenance paths.
7. Client index failure displays confirmed chain evidence plus a same-payload repair action, never a success toast or new create action.

### Acceptance

Only a fully decoded, canonical devnet create can create or return an on-chain row. Atomic duplicates converge to one canonical row and response.

## WU-4 — Human Approval, One Broadcast, and Initial Index Mutation

**Dependencies:** WU-3  
**Files:** None.

### Mandatory checkpoint

Using the deployed flow:

1. Enter and lock `Hermes Proof Token`, `HPT`, `🚀`, URI `""`.
2. Generate exactly one in-memory candidate mint.
3. Verify devnet genesis, prepare the legacy transaction, simulate unsigned, estimate fee/rent, and prove the wallet retains `0.01 SOL`.
4. Present the exact summary from WU-1.
5. Wait for explicit user approval on that exact summary.

The wallet prompt may open only after approval. The user handles wallet permission/signature UI.

### Execution

1. Immediately apply the mint signature and request one wallet signature.
2. Capture repair record and signed transaction ID before sending.
3. Broadcast once.
4. Reconcile confirmation using signature, blockhash, and last-valid block height.
5. If confirmed, make the initial `/api/tokens/index` mutation with the captured exact payload and persist its non-secret outcome.
6. If send/confirmation is ambiguous:
   - enter `reconcile_only`;
   - query through blockhash expiry;
   - never resend, re-sign, or regenerate.
7. If indexing fails after confirmed creation, preserve confirmed evidence and same index payload; do not report “live.”

### Acceptance

For this operation there was one target mint, one wallet-signing event, one broadcast attempt, and at most one successful `create_token`. No trade, migration, or replacement transaction was attempted.
